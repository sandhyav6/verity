## Indexing and resolution

* **Event indexing lag** (transaction mined -> visible through the API), 20 trades: p50 827.23 ms, p95 1015.76 ms, max 1064.6 ms. The indexer polls every 0.2 s with 0 confirmations, so the poll interval alone does not explain ~0.8 s; a profiled indexing cycle was ~155 ms and RPC calls 4-11 ms, and the remaining gap is unexplained (not proven to be machine contention). On Sepolia add the confirmation depth (about 12 blocks).
* **Resolution evidence processing** (`POST /resolutions/{id}/propose`: validate, build, hash, store), 20 runs: p50 75.54 ms, p95 90.53 ms.
* **Finalize mined -> market visible as resolved** through the API: 858.1 ms (single run).
* Registering a market definition (`POST /markets`): 47.0 ms (single run).
* **Data ingestion** (live Open-Meteo fetch + normalize, 5 runs): p50 249.03 ms, p95 789.77 ms, max 789.77 ms; record status `valid`. Dominated by network latency and the provider.

## Reading these numbers honestly

* Single machine, loopback networking, one client, warm caches; production latency would add network and TLS.
* Gas numbers are from the in-process network with default settings; real networks differ slightly (calldata, access lists) but not in kind.
* The synthetic database shows how the indexes behave at roughly 200 k trades; it is not a load test of concurrent users (none was run).
* The LMSR TypeScript numbers measure the indicative browser maths, not the on-chain pricing; the contract's accuracy is tested against the 50-digit reference in `contracts/test/`.
